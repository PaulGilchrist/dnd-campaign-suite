# AI map GENERATOR writes encounter tokens into the invisible `doc.items` lane — generated creature tokens never render (and crash outdoor maps)

### Summary
The AI designer's map-generation pipeline (`applyMaps.js` → `dressTokens`) still writes encounter/creature tokens into the legacy `doc.items[]` lane of generated dungeon maps. That lane has ZERO renderers app-wide (the sibling AI **dress** face was fixed TODAY in 33b3d0326 by routing token ops into `placedItems` — the one lane everything renders; the generator face was explicitly left as a residual, see `resolved/bug-ai-dress-tokens-invisible-write-only-lane.md` §Residuals and playbook §2330). GMs who generate a map whose dressing plan includes tokens get rows that persist into the document and are permanently invisible — and because the generator's own prompt/schema actively OFFER `tokens[]`, a real model can emit them at any time. Bonus twin found while probing: the same lane on an **outdoor (hex)** mapPlan is not even write-only — it throws a mid-batch `TypeError` AFTER the pre-apply snapshot has been taken.

### Expected behavior
A token the generation schema/prompt offers, the referential gate validates, and the applier "successfully" writes should be visible once the draft map is approved — exactly what the dress face now delivers post-33b3d0326 (monster tokens render as npc-circle + purple `.monster-circle` + ☠ in 2D, purple meshes in 3D, GM right-click Hide/Show/Delete). And an op the generator cannot support on a hex map should fail with an honest pre-write validation error, like the `placedItemOps are dungeon-only` sibling.

### Actual behavior
Dungeon generation succeeds with zero feedback and the creature rows accumulate in `doc.items[]` forever, invisible in 2D (`PlacedItems.jsx` renders the `placedItems` prop only), invisible in 3D (`Map3D.jsx:72` feeds the scene `items: placedItems`), and unreachable by any UI removal affordance. The ONLY `mapData.items` consumer app-wide is the SSE adoption at `useSSESync.js:55` (kept for exactly these generator-era docs — this bug's lane is the last writer). Hex generation with tokens crashes mid-apply after the snapshot.

### Likely location
All verified against current code (post-33b3d0326):
- `server/services/ai/authoring/applyMaps.js:146-162` — `dressTokens` pushes `{id: ai-token-<name>-<i>, name, type:'monster', gridX, gridY, fromEncounter, visible}` into **`doc.items`** (:152); called unconditionally at :179 (no outdoor guard, unlike :178's placedItemOps guard).
- `applyMaps.js:43-54` — hex doc built WITHOUT an `items` key → the outdoor TypeError (live-probed, step 8); `:74` dungeon doc seeds `items: []` — the dead lane the generator still feeds.
- The lane IS offered to the model: `entitySchemas.js:286-299` (`mapPlanSchema.dressing.tokens`, requires encounterName/creatureName/gridX/gridY), `designerPrompts.js:75` (`mapPlan{…dressing{pois[],placedItemOps[],tokens[]}}` — batch rule 5 + resume field rule), `referential.js:238-242` validates `encounterName` against existing/batch encounters (i.e. the lane is expected to be used).
- No renderer: `src/components/map/PlacedItems.jsx` (placedItems only), `src/components/map/Map3D/Map3D.jsx:72`, sole consumer `src/components/map/hooks/useSSESync.js:55`.
- Fixed sibling to mirror: `server/services/ai/authoring/dressMap.js:150-166` (`addToken` → placedItems creature rows).

### Suggested fix
Mirror the dress-face routing (Option 1 of the resolved dress bug):
1. In `dressTokens`, push into `doc.placedItems` shaped exactly like `dressMap.js addToken` (`id: aiId('token', doc.name, i)` (keep the stable id idiom or reuse `freshId`), `name: tok.creatureName`, `type:'monster'`, `gridX`, `gridY`, `visible:true`, keep `fromEncounter` — every label/menu/3D surface already rides that shape).
2. Gate tokens indoor-only for hex, next to the placedItemOps guard (applyMaps.js:178): `else if (d.tokens?.length) errors.push('<name>: tokens are dungeon-only (hex maps carry terrain + POIs)')` — turns the post-snapshot TypeError into an honest all-or-nothing validation error BEFORE any write.
3. Coherence notes: `buildMapDigest` already sources `tokens.rows` from `placedItems` (`TOKEN_TYPES`, dressMap.js:76) and the client preview/`laneRows` resolve against `placedItems` — routed rows instantly become visible to the dress-refine digest too (GM can later move/remove generated tokens via AI Dress citing real ids). No client change needed (monster rendering landed with 33b3d0326). Keep the `useSSESync` legacy `items` adoption for pre-fix docs, and per the dress-run convention wipe `ai-token-*` orphans when restoring baselines.
4. Tests: `applyMaps.test.js:68` pins `doc.items` — move that pin to `placedItems` (+ add the hex-tokens rejection case and a monster-shape/label pin).

### Severity
Broken feature — the GM approves a generated map whose encounter dressing silently vanishes (same severity class as the dress-face bug fixed today, with a wider blast radius since generation is the FIRST authoring surface a new campaign sees); the outdoor face additionally corrupts the apply lane post-snapshot. Residual of 33b3d0326, explicitly not covered by that fix.
